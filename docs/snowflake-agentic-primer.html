At the top a Cortex Agent object reasons and orchestrates; below it, everything the agent may touch is a governed function; those functions read a governed semantic model and a queryable knowledge graph; all of it sits over the OSDU/PDM canonical tables inside one RBAC boundary. The one invariant that makes this safe: the agent selects governed tools, it never writes SQL and never invents numbers. What agents are built — and what Snowflake offers

Snowflake exposes agentic intelligence at three tiers. This build instantiates the first two and positions the third; all share the same governed-tool contract.

Cortex Agent (built ★)

A first-class server-side AGENT object that plans, calls tools, and narrates. OAG_FABLE.KNOWLEDGE.PRODUCTION_AGENT — the delegated entry point an external orchestrator hands a whole question to.

sql/07_agent.sql

Cortex COMPLETE (built ★)

The LLM as a SQL function — SNOWFLAKE.CORTEX.COMPLETE(model, prompt). The client-side ProductionAgent uses it as a router (structured-output completion) with no endpoint to provision.

agent/agent.py

Cortex Analyst (positioned)

Native text-to-SQL over a semantic model — the NL→query analogue of Databricks Genie. The six SEMANTIC views are ready to back a cortex_analyst_text_to_sql tool for ad-hoc questions beyond the governed themes.

agent/README.md · "Remaining"

PRODUCTION_AGENT — the Cortex Agent object

Created from a YAML specification inside SQL DDL: an instructions block (orchestration policy + response style + sample questions), an orchestration budget, a tools list of generic tool specs, and a tool_resources map binding each tool name to a governed Snowflake function. It carries all six use-case themes plus the four knowledge-graph tools — thirteen in total.

Finding — a UDTF cannot be attached directly. The generic-tool runner invokes a function scalar-style, so a table function raises "Unknown user-defined function". The fix is a thin scalar wrapper (SURVEILLANCE_BELOW_EXPECTED_ROWS, sql/07) that returns the governed rows as an ARRAY of OBJECTs whose keys are exactly the answer-submission value_keys — so the REST adapter is trivial and the graded values keep full float precision.

The deterministic-answer / LLM-reasoning split

The design principle that survives every tier: the LLM reasons (routes across themes, resolves entities, writes the narrative) but the graded values are assembled from the governed tool result, never from the model's prose. That keeps functional correctness objective even when the whole question is delegated to the agent object.

Agent-to-agent: the REST hand-off an external orchestrator calls

The response carries the governed rows in a tool_result content item; the caller reads exact key_values from that JSON payload, never from the LLM's sentence. The agent even composes the graph tools unprompted — it plans kg_resolve("AkerBP"), kg_resolve("NO 15/9-F-12"), then kg_path(well:12 → operator:AkerBP, 6) and answers "directly operated by AkerBP — a single OPERATED_BY hop".

⚠ Account finding — Cortex COMPLETE tool-use

On this account no Cortex COMPLETE model accepts the OpenAI-style tools parameter (claude-sonnet-4-5, mistral-large2, llama3.x, openai-gpt-4.1 all reject it). So the client agent routes with a structured-output completion instead of a tool-calling loop. Native tool-use does exist at the Agent-object tier — PRODUCTION_AGENT plans and calls tools correctly.

Six themes, one contract

Both the REST and driver paths return the neutral answer_submission schema and grade against the frozen gold — 12 / 5 / 1 / 8 / 11 / 3 flagged rows, exact set + values within 1e-6. Field scoping and honest abstention are preserved: an unknown field yields clarification-requested, not a guess.

what they stand on · the context

The governed tool surface

An agent's "context" here is not a prompt blob — it is the set of governed functions it is allowed to call. Thirteen tools in OAG_FABLE.KNOWLEDGE: nine analytics answers (the six themes, three with extra groupings) and four graph-navigation tools. Each is an owner's-rights UDF/UDTF that reproduces the deterministic reference-compile, so a tool call is a governed answer.

A governed tool reads the semantic layer — it never authors SQL

The hero tool is a UDTF whose body is a SEMANTIC_VIEW() read of the governed surveillance metrics. The window and threshold come from DATASET_PARAM (governed data, not literals), so the only argument is the optional field scope. Its output columns are exactly the answer-submission flagged shape.

NL → governed metric: the business vocabulary

Term resolution maps a business phrase onto a governed metric so the agent can stay in ubiquitous language. RESOLVE_TERM('watering out') and its synonyms resolve by longest-match substring — mirroring the shell's in-memory LPG.

what they stand on · the semantic model

The semantic model — Snowflake Semantic Views

A Semantic View is Snowflake's governed metric object: first-class SQL DDL declaring TABLES, typed RELATIONSHIPS, DIMENSIONS, and METRICS — with primary keys required and derived metrics expressed by reference. Six views carry the OSI KPI set; agents (and Cortex Analyst) select these governed metrics rather than authoring aggregation SQL.

Metrics reference metrics — closer to the neutral OSI spec than a flat re-aggregation

The sharpest modeling difference from Databricks Metric Views: Snowflake rejects SUM(metric). A ratio metric must reference base metrics — which is exactly how OSI defines ratio/derived types. The hero view declares two base sums and two derived metrics that reference them.

Reading a Semantic View — filters go inside the function

You name dimensions and metrics inside the SEMANTIC_VIEW() table function; row-level filters go in its inner WHERE, and an outer WHERE only filters the aggregated output. This query reproduces gold/surveillance.json — the 12 flagged wells — exactly.

A Semantic View logical table must reference a table or view (unlike a Metric View's arbitrary inline source: SQL). The three metrics with bespoke shapes — the surveillance union, the forecast/allocation join+filter — become named backing views _SURVEILLANCE_SRC / _FORECAST_SRC / _ALLOCATION_SRC, with a ROW_NUMBER() surrogate key where the union has no natural PK. All in-locus in the semantic layer; no OSI construct failed to translate.

what they stand on · the knowledge graph

The knowledge graph — an explicit, queryable LPG

Where the Semantic Views declare the same joins per view for the metric engine, the knowledge graph holds every business concept and relationship once, account-wide, as a Labeled Property Graph the agent can walk. It's the KG_NODE/KG_EDGE pattern — derived deterministically from the canonical tables, so graph and substrate cannot drift.

Nodes and edges built from canonical FK columns

Node ids are '<type>:<key>' strings so one column references any entity type; field nodes carry their synonyms as a property (feeding kg_resolve). Informational PK/FK constraints keep the graph discoverable from INFORMATION_SCHEMA.

Traversal is a cycle-guarded recursive CTE — the agent walks it without table access

Four owner's-rights UDTFs — KG_RESOLVE, KG_NEIGHBORS, KG_TRAVERSE, KG_PATH — treat edges as bidirectional and guard cycles by array membership. They answer entity-resolution and relationship questions server-side.

what they stand on · the boundary

The governance boundary — owner's rights as a security wall

The strongest Snowflake finding for agentic workloads: because SQL UDFs run with the owner's rights, the governed tools become a security boundary, not a convention. The agent role can call every tool yet cannot SELECT a single raw table — the tightest possible form of "governed tools, no SQL authoring". Three least-privilege roles carry it.

RBAC gotcha. Snowflake sessions default to secondary roles = ALL (the union of every role a user holds), so a broad role can leak in and make least-privilege appear to pass when it doesn't. Test isolation with USE SECONDARY ROLES NONE, and give the agent's service user a scoped default role.
