Primer · what's built, and what it shows

Production data, given meaning an agent can use

A reference build for oil and gas production surveillance: OSDU canonical tables, one governed definition of each KPI, a standards-based ontology that reasons over the asset hierarchy, rules and constraints written as data, and agents on Snowflake, Fabric and Claude that answer from all of it. Every answer is graded against gold the data generator wrote.

The stack

Six layers, each with one job

A question falls through the stack from the agent down. The agent never computes a number: it picks a governed tool. Meaning (what a field is, what "below expected" means, which OSDU record is which well) comes from the knowledge layer. Numbers come only from the metrics layer, over the canonical tables.

AgentsClaude, Snowflake Cortex Agent, Fabric custom agent: pick governed tools, build graded answers in code PlatformsSnowflake and Fabric: semantic models plus the ontology's knowledge, generated as views Rules & constraintsbusiness terms as dated flags (SHACL rules); data-quality shapes (SHACL) OntologyOWL 2 RL classes, keys and properties; SKOS vocabulary; R2RML mapping; reasoning in-process or on GraphDB Governed metricsOSI-style YAML: each KPI defined once, compiled to SQL Canonical tablesOSDU Production Data Model, written deterministically with gold answers

1 · Canonical tables

One system of record, and the answers it should give

The generator writes nine OSDU Production Data Model tables as Parquet: three fields (Volve, Sleipner, Gullfaks), 18 wells, 6 facilities, three operators and over a year of daily volumes. It is deterministic, so the same config gives the same bytes. Alongside the tables it writes gold: the answer to every catalog question, from its own knowledge of what it generated (for example, which wells it made under-perform). Every platform loads the same files.

2 · Governed metrics

Each KPI is defined once

Metrics are YAML over the canonical tables: simple measures, ratios and derived metrics. The reference compile turns them into SQL on DuckDB; each platform translates the same definitions into its own semantic model. Production efficiency is a ratio of two governed metrics, and "below expected" will be defined in terms of it.

The hero question, which wells produced below expected oil this week, and by how much?, compiled from those metrics over 25–31 March 2025: 12 wells flagged, equal to gold. Six use cases are built this way: surveillance, deferment by cause, 12-month decline, well-test anomalies, a watchlist, and the roll-up by field and operator.

3 · The ontology

Meaning the platforms don't carry

The knowledge layer uses W3C standards, so it isn't tied to one engine: RDF, OWL 2 RL, SKOS, R2RML and SHACL. It is four files plus a vocabulary.

filewhat it holds
oag.ttlthe schema: Well, Facility and Field are subclasses of Asset; partOf is transitive, with inField and atFacility beneath it; inverses (hasPart, operates); keys; each class aligned to its OSDU kind
mapping.r2rml.ttlhow canonical rows become instances, so the graph is built from the tables
vocabulary.yaml → SKOSfield synonyms; business terms (metric, comparison, threshold); the product hierarchy
rules.ttl, shapes.ttlSHACL rules (business terms) and SHACL constraints (data quality)

After mapping, well 1 has only what its row says: type Well, its UWI, a link to facility 1 and to field 1, and operator Equinor. Nothing says it's an asset, that it's part of the field through its facility, or which OSDU record it is. Reasoning adds those.

Finding · key rules

Neither engine's built-in key rule could be relied on. owlrl's makes every well the same as every other (ADR 0042); GraphDB's misses some facility links on the two-property key, differently on each load (ADR 0051). The key rule is applied in code before reasoning, on both engines.

4 · Rules

"Below expected", as data and as a rule

A business term holds for a well over a period, so it's recorded as a dated flag, never as class membership (ADR 0041). The numbers come from the governed metrics; the graph only compares them. The term runs two ways, and both must equal gold:

  • Definition as data: read the term's SKOS definition (metric, comparison, threshold) from the graph, and apply it in code.
  • SHACL rule: a sh:SPARQLRule constructs oag:Flag records over per-well period records.

Result: wells 1, 2, 5, 6, 7, 8, 9, 10, 11, 12, 13 and 17, by definition, by rule and in gold. agree Each flag is a record such as flag/below_expected/well/6/2025-03-25/2025-03-31, efficiency 0.319.

5 · Constraints

SHACL catches bad data before it's answered

Shapes state what must be true: every well in exactly one field, a well's field equal to its facility's, no shared keys, and SPARQL checks over the daily records. The generator can plant faults and record them as gold, so the shapes are graded too. On a dataset with planted faults, the shapes find exactly the gold findings:

6 · A second engine

GraphDB, with the daily volumes served in place

The same files run on GraphDB 10.8: its OWL 2 RL ruleset does the reasoning, its SHACL engine runs the shapes, and an Ontop repository serves the daily volumes live from DuckDB through an R2RML mapping, so they are never copied into the graph. The knowledge API wraps GraphDB's SPARQL endpoint, so every question runs unchanged and gets the in-process answer.

Oil by field this month, hybrid query against the governed roll-up: Gullfaks 1,538,397 bbl, Sleipner 1,057,821, Volve 326,809. equal The exception to portability is SHACL rules (a W3C Note), which GraphDB doesn't run.

7 · Knowledge on the platforms

The ontology's answers, generated as views

Snowflake, Fabric and Databricks have no OWL reasoner. So the ontology's knowledge is generated for them, from the same files: views for the class hierarchy (entity, asset), the part-of closure (part_of), identity on the keys (same_as), and tables for synonyms, terms and products. One generator, three SQL dialects. Each deployed platform's views are then checked live against the in-process ontology.

8 · Platform semantic models

The same metrics, in each platform's own model

Hero question through each: Snowflake Semantic View flags the 12 gold wells = gold; Fabric DAX flags the same 12 = gold. Fabric also has its own Fabric IQ ontology item (entities, relationships, rules), queried over MCP; its custom agent uses it to resolve names ("the volve" → field 1, Volve).

9 · The agents

Three agents, the same questions, graded against gold

Each agent answers through governed tools. The model chooses the tool; the graded rows are built in code from the tool's result, never from the model's prose. So a wrong number can only come from a wrong tool choice, which the grading catches.

Finding · a harness that was too kind

The first run of this primer scored the Snowflake agent 4/6. Its own test harness had asked a reworded decline question and graded only each question's first set, so it had reported 6/6. Asked the catalog's words, the agent tried to resolve "Field X" as a name; and the by-operator roll-up rows were never graded. Its instructions now say what "Field X" means, as the other agents' do, and the harness asks the catalog's text and grades every set; a test pins both (ADR 0049). The rerun above scores 6/6.

The ontology agent is also asked questions only reasoning can answer, graded against answers computed from the canonical tables directly: every asset in a field (inheritance and the part-of closure), wells by field and operator, facilities by operator, the products in total liquids, and which well an OSDU record is. 5/5

What it shows

What the build demonstrates

Governed numbers

One definition of each metric reproduces gold on every platform deployed. The governed layer decides the numbers, not the model.

Reasoning adds meaning

Inheritance, a transitive roll-up, inverses, identity across systems from keys, and business language mapped to metrics: all inferred from four standard files, none stated in any table.

Rules and constraints are data

"Below expected" agrees as a definition and as a SHACL rule; the SHACL shapes find exactly the planted faults.

Standards are portable, with checks

GraphDB gives the in-process answers and the agent scores the same on it. Where an engine's rule can't be relied on, it's applied in code and tested.

Generated knowledge travels

The platforms get the ontology's answers as views, checked against the ontology, and their agents answer the asset-knowledge questions from them. What they don't get is reasoning at query time: the ontology agent can still write its own SPARQL.
